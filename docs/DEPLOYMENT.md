# Production-развёртывание Գրքասեր

Базовый `infra/docker-compose.yml` предназначен также для локального запуска. Production-настройки находятся в версионируемом `infra/docker-compose.production.yml`; их необходимо подключать **вторым файлом**. Настоящий `.env`, пароли, database dumps и ключи SSH не хранятся в Git.

## Существующая установка на сервере

На текущем сервере используется `/opt/grqaser/compose.sh`: он читает секретный `/opt/grqaser/.env`, задаёт проект `grqaser` и объединяет `/opt/grqaser/app/infra/docker-compose.yml` с **внешним** `/opt/grqaser/compose.production.yml`. Внешний override не обновляется автоматически командой `git pull` внутри `/opt/grqaser/app`.

Версионируемый `infra/docker-compose.production.yml` служит проверяемым шаблоном. При обновлении внешний override нужно отдельно сравнить с шаблоном, сохранить старую копию и применить необходимые изменения. Не заменять `/opt/grqaser/.env` примером из Git и не перезаписывать helper без проверки.

Для текущего предпросмотра внешний override явно фиксирует `https://grqaser.digitalize.am` для URL/CORS и строку `"false"` для индексации **в build args и runtime**. При окончательном переключении домена потребуется изменить также этот реально используемый override либо перейти на версионируемый env-управляемый шаблон. Изменение только `.env` не перекрывает жёстко заданные значения внешнего override.

В существующей установке запуск через helper сохраняет реальные пути и проект:

```bash
/opt/grqaser/compose.sh config --quiet
/opt/grqaser/compose.sh up -d --build
/opt/grqaser/compose.sh ps
```

Команды ниже с двумя `-f` — эквивалент для установки, которая **действительно использует версионируемый override**, а не повод незаметно менять текущую схему.

## Домен и индексация

До готовности DNS и HTTPS `grqaser.am` использовать действующий адрес предпросмотра:

```dotenv
NEXT_PUBLIC_SITE_URL=https://grqaser.digitalize.am
LUMI_CORS_ORIGINS=https://grqaser.digitalize.am
SITE_INDEXING_ENABLED=false
```

Canonical должен указывать на доступный адрес текущего сайта. Не включать перенаправление на `grqaser.am`, пока тот не проверен по HTTPS. Production override по умолчанию предполагает окончательный адрес `https://grqaser.am`, поэтому для существующего предпросмотра обе переменные URL выше задаются явно.

При окончательном переходе, после проверки DNS, сертификата, реального каталога, контактов и оформления заказа:

```dotenv
NEXT_PUBLIC_SITE_URL=https://grqaser.am
LUMI_CORS_ORIGINS=https://grqaser.am
SITE_INDEXING_ENABLED=true
```

`SITE_INDEXING_ENABLED` и `NEXT_PUBLIC_SITE_URL` передаются одновременно в **build args и runtime web**. Для любого изменения этих значений требуется **новая сборка web**, затем пересоздание контейнера. Next.js записывает `headers()` в результат сборки, а публичные переменные могут встраиваться в клиентские пакеты. `docker compose restart web` не заменяет сборку и не применяет новые environment-переменные.

Опциональные `GOOGLE_SITE_VERIFICATION` и `YANDEX_SITE_VERIFICATION` берутся из владельческого аккаунта поискового сервиса; не придумывать значения. Реальные контакты и URL документов передаются существующими `LUMI_CONTACT_*`, `LUMI_TERMS_URL`, `LUMI_PRIVACY_URL`, `LUMI_RETURNS_URL`. Подробный порядок индексации — в [SEO_LAUNCH.md](SEO_LAUNCH.md).

## Сеть и безопасность

- PostgreSQL, Redis, API и web публикуют порты только на `127.0.0.1`. Наружу выходят только необходимые SSH и HTTP/HTTPS reverse proxy; не открывать 3000/4000/55432/56379 в firewall.
- Override закрепляет сеть `172.18.0.0/16`, gateway `172.18.0.1`, как на текущем production. Перед применением на другой машине проверить конфликт с существующими Docker/VPN-сетями. Не удалять занятую сеть для обхода конфликта.
- API доверяет forwarded-заголовкам только от `172.18.0.1/32`. При смене сетевой схемы сначала определить реальный peer reverse proxy, затем явно изменить CIDR; не использовать доверие всем IP и не доверять всем контейнерам подсети.
- Хостовый reverse proxy должен сам устанавливать `Host`, `X-Forwarded-Proto` и цепочку адресов клиента. Не принимать произвольные значения этих заголовков от внешнего запроса как доверенные.
- Production-логи Docker ограничены `10m × 3` для каждого сервиса. Долгоживущие сервисы используют `restart: unless-stopped`; миграции — одноразовый сервис без бесконечного перезапуска.
- Production worker настроен с `WORKER_ENABLED=false` и `restart: "no"`: он не импортирует демонстрационные fixtures. Это не HTTP-сервис; без фоновой работы он штатно завершает процесс, поэтому состояние `Exited (0)` ожидаемо, а не является ошибкой. При отдельно разрешённом включении реальной фоновой работы нужно явно вернуть `restart: unless-stopped` и согласовать режим worker с разрешениями crawler. Live crawler остаётся отдельно permission-gated и выключен по умолчанию. Эта инструкция не включает парсинг или закупки.
- Заменить development-пароль PostgreSQL и все admin placeholders уникальными секретами. Согласовать `LUMI_DATABASE_URL` с реальными реквизитами, корректно URL-кодировать спецсимволы. Ограничить права `.env` владельцем файла.

## Обновление существующей установки

Команды ниже выполняются из корня клона. Они предполагают проверенное имя существующего Compose-проекта `grqaser`. Если установка использует другое имя, подставить **именно существующее**: изменение project name создаёт другую сеть и другие volumes, а не переносит данные.

1. Проверить локальные серверные изменения и версию Git. Не делать `reset --hard` и не перезаписывать непроверенные изменения. Не добавлять `.env` в commit.
2. До миграций сделать резервную копию PostgreSQL и проверить восстановление. Сохранить предыдущую версию приложения/образа. Не считать Docker volume резервной копией.
3. Проверить конфигурацию, не выводя пароли в терминал или чат:

```bash
docker compose --env-file .env -p grqaser \
  -f infra/docker-compose.yml -f infra/docker-compose.production.yml config --quiet
```

4. Собрать и запустить выбранную версию. Новый образ web обязателен при изменении публичного URL или индексации:

```bash
docker compose --env-file .env -p grqaser \
  -f infra/docker-compose.yml -f infra/docker-compose.production.yml up -d --build
```

`migrate` дожидается PostgreSQL и применяет versioned migrations; API запускается только после успешного завершения миграций. Не игнорировать ошибки миграций. Команда `down -v` уничтожает volumes — её не использовать для обновлений.

5. Проверить состояние контейнеров и адреса без вывода `.env`:

```bash
docker compose --env-file .env -p grqaser \
  -f infra/docker-compose.yml -f infra/docker-compose.production.yml ps
curl -fsS http://127.0.0.1:4000/api/v1/health/ready
```

Не публиковать полный вывод `docker compose config`, `docker inspect` или environment контейнеров: там могут быть секреты. Для проверки конфигурации использовать `config --quiet` или выводить только заранее выбранные несекретные поля.

## Контроль SEO после сборки

Пока это предпросмотр, ожидается `X-Robots-Tag: noindex, nofollow` для `/hy`, запрет обхода в robots и `404` у sitemap:

```bash
curl -I https://grqaser.digitalize.am/hy
curl -fsS https://grqaser.digitalize.am/robots.txt
curl -I https://grqaser.digitalize.am/sitemap.xml
```

После перехода на новый домен и включения флага:

```bash
curl -I https://grqaser.am/hy
curl -fsS https://grqaser.am/robots.txt
curl -fsS https://grqaser.am/sitemap.xml
curl -I https://grqaser.am/ru/cart
```

Публичная главная не должна иметь `noindex` ни в HTTP-заголовке, ни в HTML. Корзина, аккаунт, поиск и админка должны сохранить `noindex`. Проверить canonical именно в HTML, а не только в переменных окружения. Ошибка sitemap `503` требует исправления доступа к API; отключённый sitemap `404` требует проверки флага и используемого образа.

Только после успешных проверок настроить постоянный `301`/`308` со старого хоста на новый с сохранением пути и query string. Сохранить рабочие DNS/TLS старого домена для редиректа. Не перенаправлять все страницы на главную и не создавать петлю между доменами.

## Возврат к предыдущей версии

При ошибке сборки или запуска оставить предыдущий работающий релиз и не менять DNS/редиректы. Откат приложения не означает откат уже применённых миграций: предварительно проверить совместимость схемы. Не восстанавливать старую БД поверх новых заказов без согласованного плана восстановления.

## Известное предупреждение зависимостей

На 24 сентября 2026 года аудит API сообщает три связанные high-записи в цепочке `prisma → @prisma/config → deepmerge-ts`. [GHSA-ggr8-5vv4-36mx](https://github.com/advisories/GHSA-ggr8-5vv4-36mx) касается истощения стека при рекурсивных графах объектов; исправленная версия `deepmerge-ts` — 8.0.0. Простого JSON для этого сценария недостаточно, и достижимость из HTTP API данного проекта не доказана. Это остаётся известным предупреждением, а не основанием считать зависимости полностью безопасными.

Не запускать `npm audit fix --force` и не навязывать несовместимую major-версию транзитивной зависимости. Обновление Prisma/совместимого дерева нужно проверять отдельно с генерацией клиента, миграциями и тестами PostgreSQL. Аудит web и worker на момент проверки не выявил уязвимостей; результаты следует обновлять перед следующими релизами.
